# Lesson 1.7: 단일 vs 다중 에이전트 아키텍처 (Single Versus Multi-Agent Architectures: Choosing the Right AI Workflow) 📐

모듈 1의 마지막 레슨으로, AI 에이전트가 작업을 수행하기 위해 어떻게 관계를 맺고 작동하는지 결정하는 **에이전트 아키텍처(Agent Architecture)**의 두 가지 유형(단일 vs 다중 에이전트)을 비교하고 올바른 워크플로우 선택법을 알아봅니다.

---

## 1. 에이전트 아키텍처의 정의

* **에이전트 아키텍처:** AI 에이전트들이 주어진 복잡한 작업을 효율적으로 완료하기 위해 **어떻게 조직되고 상호작용하는지를 정의하는 시스템 구조(Framework)**입니다.

```
[ 단일 에이전트 아키텍처 (Single-Agent) ]
사용자 요청 ➡️ 단일 에이전트 (추론 + 계획 + 행동 + 도구) ➡️ 완료

[ 다중 에이전트 아키텍처 (Multi-Agent) ]
                    ┌── 에이전트 A (특화 도구 A)
사용자 요청 ➡️ 관리자 ┼── 에이전트 B (특화 도구 B) ➡️ 협업 및 피드백 ➡️ 완료
                    └── 에이전트 C (특화 도구 C)
```

---

## 2. 단일 에이전트 아키텍처 (Single-Agent Architecture)

* **개념:** 하나의 AI 에이전트가 추론(Reasoning), 계획(Planning), 행동(Action)을 모두 독립적으로 도맡아 처리하는 구조입니다.
* **대표 예시:** ReAct 패턴을 활용한 자율 에이전트.
* **적합한 상황:** 연동하는 도구가 많지 않고, 워크플로우가 명확하며, 상대적으로 간단한 솔루션을 빠르게 개발하고자 할 때.

### ➕ 장점
* **극도의 단순성:** 관리해야 하는 엔티티가 하나뿐이므로 구현, 모니터링, 평가 및 테스트가 매우 간편합니다.
* **연산 리소스 효율성:** 에이전트 간의 대화나 중개(Orchestration) 과정에서 발생하는 오버헤드(Overhead) 비용이 없습니다.

### ➖ 한계
* **복잡한 작업의 한계:** 수많은 단계가 필요하거나 장기 기억이 요구되는 작업을 독자적으로 처리할 때 성능이 하락합니다.
* **도구 포화 병목 현상:** 사용할 수 있는 도구가 너무 많아지면(Tool Saturation), LLM의 정확도가 크게 저하됩니다.
* **병렬 처리 불가:** 모든 일이 단일 루프 안에서 한 번에 한 단계씩 순차적으로 진행되므로 멀티태스킹이 불가능합니다.

---

## 3. 다중 에이전트 아키텍처 (Multi-Agent Architecture)

* **개념:** 특정한 역할에 최적화된 둘 이상의 에이전트가 네트워크를 형성하여 협력 및 의사소통하는 구조입니다.
  * **수직적 구조 (Vertical):** 리더 에이전트의 지휘 아래 계층(Hierarchy) 구조로 구성.
  * **수평적 구조 (Horizontal):** 동등한 자격을 갖춘 피어(Peer) 에이전트들이 자율적으로 협동.
* **특징:** 각 에이전트는 서로 다른 LLM, 프롬프트, 도구 모음을 맞춤형으로 사용할 수 있습니다.

### ➕ 장점
* **작업의 병렬 처리 (Parallelism):** 동시에 여러 하위 태스크를 병렬 분산 처리할 수 있어 속도가 향상됩니다.
* **역할의 견고성 (Robustness):** 각 에이전트가 자신이 가장 잘하는 세부 전공 분야(Specialty)에만 집중하므로 모듈별로 높은 완성도를 가집니다.
* **유연한 확장성 (Scalability):** 새로운 도메인의 에이전트를 모듈식으로 추가하기 편하며, 서로 다른 서버에서 독립적으로 구동할 수 있습니다.

### ➖ 한계
* **높은 구현 난이도:** 에이전트 간의 대화 규칙, 정보 교환 포맷, 전체적인 **오케스트레이션(Orchestration)** 워크플로우를 신중하게 설계해야 합니다.
* **신뢰성 전파 실패 (Cascading Failure):** 하나의 특화 에이전트가 예기치 않게 실패하면, 도미노처럼 시스템 전체의 연쇄 실패를 일으킬 수 있습니다.

---

## 4. 단일 에이전트 vs 다중 에이전트 비교 요약

| 비교 항목 | 단일 에이전트 (Single-Agent) | 다중 에이전트 (Multi-Agent) |
| :--- | :--- | :--- |
| **구현 난이도** | 🟢 매우 쉬움 | 🔴 어려움 (오케스트레이션 필요) |
| **구동 효율성** | 🟢 높음 (연산 오버헤드 없음) | 🟡 낮음 (에이전트 간 통신 비용) |
| **복잡 태스크 처리** | 🔴 한계 존재 (루프 포화) | 🟢 뛰어남 (분할 및 협업 가능) |
| **동시 병렬 실행** | 🔴 불가 (순차 실행) | 🟢 가능 (동시 다발 처리) |
| **도구 수용 한계** | 🟡 적은 수의 도구에 강함 | 🟢 많은 도구를 분산하여 수용 가능 |
| **시스템 확장성** | 🔴 제한적 | 🟢 매우 뛰어남 (모듈식 확장) |

---

## 💡 올바른 아키텍처 선택을 위한 3가지 기준

1. **작업의 복잡성 (Task Complexity)**
   * 단일하고 명확한 목표 ➡️ **단일 에이전트**
   * 여러 개의 독립적인 세부 목적이나 다방면의 전문성이 결합된 목표 ➡️ **다중 에이전트**
2. **도구의 다양성 (Tooling Needs)**
   * 1~3개의 집중된 도구 세트 사용 ➡️ **단일 에이전트**
   * 수많은 서로 다른 도구를 동적으로 교차 호출해야 하는 워크로드 ➡️ **다중 에이전트** (작업 분산)
3. **구현 속도 및 성장성 (Speed vs Scale)**
   * 빠른 프로토타입 설계 및 가벼운 동작 우선 ➡️ **단일 에이전트**
   * 장기적인 유지보수성, 유연성 및 향후 확장성 확보 ➡️ **다중 에이전트**

## 🎓 Module 1 핵심 요약 (Module 1 Summary)

이번 모듈을 학습하며 AI 에이전트의 세계로 첫걸음을 떼었습니다.

* **에이전트의 본질:** LLM을 브레인으로 삼아 스스로 계획(Planning)을 짜고, 외부 도구(Tools)를 활용해 행동(Action)하며, 루프(Iteration)를 돌며 결과를 완성해 나가는 정교한 자율 엔티티.
* **핵심 에이전틱 행동:** 복잡한 워크플로우 속에서 나타나는 **라우팅(Routing)**, **도구 선택(Tool Selection)**, **품질 검사(Quality Checks)**.
* **ReAct 패턴:** `Thought(생각) ➡️ Action(행동) ➡️ Observation(관찰)`의 끊임없는 루프를 통해 환각률을 기존 CoT 대비 **절반 이하(14% ➡️ 6%)**로 낮추고 문제 해결력을 증명하는 패턴.
* **아키텍처 선택:** 단순하고 가벼운 태스크에는 효율적인 **단일 에이전트**를, 복잡하고 확장 가능한 다중 도메인 협업 태스크에는 **다중 에이전트**를 적재적소에 배치해야 함.
