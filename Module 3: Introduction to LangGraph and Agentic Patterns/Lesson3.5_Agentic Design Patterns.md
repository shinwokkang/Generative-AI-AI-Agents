# Lesson 3.5: 에이전트 디자인 패턴 (Agentic Design Patterns) 심화 가이드 📐

이 가이드는 단순한 설명에 그치지 않고, 각 패턴이 **해결하고자 하는 비즈니스/개발적 한계(도전 과제)**, **구체적인 알고리즘 프로세스**, **실무 적용 사례(Use Cases)**, 그리고 **엔지니어링 트레이드오프(Trade-offs)**를 심층적으로 다룹니다. 이를 통해 프로덕션 레벨의 에이전트 시스템을 설계할 수 있는 실무 역량을 다집니다.

---

## 1. 계획 (Planning) 패턴

**계획(Planning) 패턴**은 최종 목표를 달성하기 위해 에이전트가 동적으로 수행할 **'일련의 행동 단계를 사전에 쪼개고 전략적으로 수립'**하는 디자인 패턴입니다.

![Planning Pattern](images/Planning.png)

### 🔴 Core Challenge (도전 과제)
단일 LLM 호출이나 단순한 ReAct 흐름만으로는 복잡한 장기 실행 과제(Long-term Tasks)를 해결하기 어렵습니다. 연산 단계가 10단계가 넘어가면 LLM은 주의력 결핍으로 인해 최초의 목표를 잊어버리거나(Lost in the Middle), 중간에 길을 잃고 엉뚱한 행동을 반복하게 됩니다.

### ⚙️ Step-by-Step 실행 프로세스
1. **초기 작업 분해 (Decomposition):** 플래너 에이전트가 사용자 요청을 분석하여 실행 가능한 하위 작업 리스트(Task List)를 동적으로 생성합니다.
2. **작업 할당 및 실행 (Execution):** 작업 실행자 에이전트(혹은 하위 에이전트들)가 현재 처리해야 할 하위 태스크를 전달받아 필요한 도구를 활용해 수행합니다.
3. **결과 피드백 및 계획 재조정 (Plan Refinement):** 실행 노드가 결과를 플래너에게 반환하면, 플래너는 그 성공/실패 여부와 새로운 정보를 바탕으로 남은 작업 리스트를 동적으로 수정(추가, 삭제, 순서 변경)합니다.
4. **종료 판단:** 모든 하위 작업이 성공적으로 완수되거나 최종 목표에 도달하면 결과를 사용자에게 반환하고 종료합니다.

### 💼 실무 유즈케이스 (Use Cases)
* **소프트웨어 개발 및 디버깅 에이전트:** 1) 요구사항 분석 ➡️ 2) 클래스 설계 ➡️ 3) 코드 작성 ➡️ 4) 테스트 코드 작성 ➡️ 5) 에러 발생 시 디버깅 계획 수립 및 디버그 실행 ➡️ 6) 검증 완료 후 배포.
* **심층 시장 분석 보고서 작성:** 특정 산업군 조사를 위해 국가별 정책, 주요 경쟁사, 시장 재무제표 조사를 차례로 기획하고 데이터 수집 현황에 따라 조사 방향을 변경하며 보고서를 작성하는 프로세스.

### ⚖️ 엔지니어링 고려사항 (Trade-offs)
* **장점:** 복잡한 대형 프로젝트를 체계적으로 수행하여 완결성을 극대화합니다.
* **단점:** 매 단계마다 계획을 검토하고 업데이트하는 LLM 호출 비용이 추가되므로 레이턴시(속도)가 느려지고 토큰 소모량이 증가합니다.

## 2. 성찰 (Reflection) 패턴

**성찰(Reflection) 패턴**은 에이전트가 완성한 결과물을 즉시 사용자에게 반환하지 않고, 리뷰어 역할의 다른 노드를 거쳐 **'자가 평가(Self-Evaluation)'** 및 수정을 거듭하여 품질을 극대화하는 패턴입니다.

![Reflection Pattern](images/Reflection.png)

### 🔴 Core Challenge (도전 과제)
LLM은 한 번에 복잡한 작문이나 코딩을 완벽하게 해내기 어렵습니다. 팩트 체크 오류(환각), 서식 누락, 코드 구문 오류 등이 초기 답변에 쉽게 포함되므로, 이를 자동 검수하고 걸러줄 수 있는 품질 보증(QA) 메커니즘이 부재하면 신뢰도가 붕괴됩니다.

### ⚙️ Step-by-Step 실행 프로세스
1. **초안 생성 (Generation):** 생성 노드(Generator)가 주어진 지침을 기반으로 산출물(코드, 글 등)을 작성합니다.
2. **비판적 성찰 (Reflection):** 성찰 노드(Reflector)가 초안을 전달받아 명확한 기준(서식 준수 여부, 사실 확인, 실행 가능성 등)에 비추어 비판적으로 평가하고, 구체적인 개선 및 피드백 지침을 텍스트로 작성합니다.
3. **개선 및 재수정 (Refinement):** 생성 노드는 피드백을 컨텍스트로 받아들이고 초안을 전면 보완하여 개선안을 작성합니다.
4. **종료 조건 매칭:** 성찰 노드가 "더 이상 개선 사항이 없다(Pass)"고 판단하거나, 사전에 지정한 최대 루프 횟수(예: 3회)에 도달하면 최종 결과물을 발행합니다.

### 💼 실무 유즈케이스 (Use Cases)
* **Self-Healing Code 에이전트:** 개발자가 작성한 코드를 입력받아 에이전트가 코드를 컴파일해 본 후, 에러 로그(Observation)를 분석하여 스스로 코드를 고쳐 쓰는 프로세스.
* **블로그/마케팅 이메일 교정:** 원문 작성 에이전트가 글을 쓰고, 교정 에이전트가 맞춤법과 타깃 독자에 맞는 뉘앙스 검수 후 수정을 유도하는 흐름.

### ⚖️ 엔지니어링 고려사항 (Trade-offs)
* **장점:** 인간의 수동 감수 작업을 획기적으로 줄이며, 산출물의 신뢰성과 일관성이 완벽에 가깝게 향상됩니다.
* **단점:** 품질 만족 시까지 루프가 무한정 돌 수 있어 타임아웃 처리가 중요하며, API 비용이 급증할 수 있습니다.

## 3. 맵리듀스 (Map-Reduce) 패턴

**맵리듀스(Map-Reduce) 패턴**은 하나의 큰 작업을 여러 개의 작은 작업으로 병렬 쪼개어 동시 처리(Map)하고, 최종 결과를 하나로 응집력 있게 수집/가공(Reduce)하는 패턴입니다.

![Map-Reduce Pattern](images/Map-Reduce.png)

### 🔴 Core Challenge (도전 과제)
대량의 파일(예: 수십 개의 소스 코드 파일)을 스캔하거나 아주 긴 논문을 요약할 때, 순차적으로 하나씩 처리하면 실행 시간(Latency)이 지나치게 길어집니다. 또한, 모든 정보를 한 번에 LLM에 욱여넣으면 컨텍스트 한계(Context Window limit)를 초과해 정보 유실이 발생합니다.

### ⚙️ Step-by-Step 실행 프로세스
1. **작업 분할 (Map / Fan-out):** 하나의 대용량 작업을 병렬로 처리 가능한 고유 조각들로 분할합니다.
2. **병렬 독립 실행:** LangGraph의 `Send` API나 서브그래프를 호출하여, 각 분할된 조각들을 전용 노드 또는 스레드에 실어 독립된 LLM/도구에서 병렬로 동시 연산합니다.
3. **동적 병합 (Reduce / Fan-in):** 모든 병렬 노드의 연산이 완료될 때까지 대기(Barrier sync)한 후, 반환된 개별 결과 리스트를 한곳에 모읍니다.
4. **최종 종합:** 수집된 리스트 데이터를 취합 노드로 넘겨, 전체 요약 보고서나 최종 결합 코드를 완성합니다.

### 💼 실무 유즈케이스 (Use Cases)
* **대형 코드베이스 보안 스캔:** 수백 개의 코드 파일을 맵 단계에서 병렬로 개별 보안 검사하고, 리듀스 단계에서 발견된 모든 취약점 목록을 종합 보고서로 취합.
* **다차원 논문 요약:** 수십 장에 달하는 논문의 장(Chapter)별 요약을 병렬 처리하고 최종적으로 단 한 장의 초록(Abstract)으로 합성.

### ⚖️ 엔지니어링 고려사항 (Trade-offs)
* **장점:** 분산 처리를 통해 레이턴시를 획기적으로 단축시킵니다.
* **단점:** 맵 단계에서 수십 개의 LLM 호출이 동시다발적으로 발생하므로 분당 토큰 제한(TPM/RPM Rate Limit)에 걸리기 쉬우며, 병렬 처리가 끝날 때까지 대기하는 동기화 시점에 병목 현상이 생길 수 있습니다.

## 4. 다중 에이전트 (Multi-Agent) 아키텍처 패턴

각각의 도구와 언어 모델로 무장한 전문성 있는 다수 에이전트가 공통 목표를 향해 협력하는 구조입니다.

![Multi-Agent Pattern](images/Multi-Agent.png)

### 🔴 Core Challenge (도전 과제)
단일 에이전트에 너무 많은 프롬프트 지침(System Prompt)과 수십 개의 외부 도구(APIs)를 쑤셔 넣으면, LLM의 상황 인지 능력이 크게 상실됩니다. 에이전트가 엉뚱한 프롬프트를 뱉거나 툴 호출 매개변수를 망가뜨리는 **도구 포화(Tool Saturation) 및 프롬프트 혼선** 현상이 발생합니다.

### ⚙️ Step-by-Step 실행 프로세스
1. **오케스트레이션 및 라우팅:** 감독 에이전트(Supervisor)가 사용자 입력을 청취하고 요구 분야를 진단합니다.
2. **작업 분배:** Supervisor는 작업을 잘 처리할 수 있는 특화 에이전트(예: 데이터베이스 에이전트, 코딩 에이전트)에게 제어권과 상태(State)를 전달합니다.
3. **독립 해결:** 위임받은 전문 에이전트는 자신에게 좁게 규정된 프롬프트와 소수의 도구(Local Tools)만 사용하여 깔끔하게 결과를 도출한 뒤 Supervisor에게 복귀합니다.
4. **종합 및 피드백:** Supervisor는 결과물을 수집해 최종 사용자에게 반환하거나, 미진한 경우 다른 전문 에이전트에게 추가 작업을 위임합니다.

### 💼 실무 유즈케이스 (Use Cases)
* **가상 제품 개발팀:** 프로젝트 매니저(Supervisor) 에이전트가 고객의 요구사항을 받아, 기획 에이전트, 백엔드 코딩 에이전트, 그리고 QA 테스트 에이전트에게 순차적으로 작업을 배정하고 최종 승인을 관리하는 시스템.
* **법률 및 세무 패키지 서비스:** 고객의 종합 자산 분석 요청을 받고, 법률 분석 에이전트와 세무 분석 에이전트가 각자의 DB 도구로 분석한 뒤 오케스트레이터가 하나의 패키지 자문서로 합성하는 구조.

### ⚖️ 엔지니어링 고려사항 (Trade-offs)
* **장점:** 에이전트별 프롬프트 크기가 극적으로 감소하여 모델이 툴을 다루는 정확도가 향상되고, 개별 모듈 단위로 고치고 테스트하기 쉬워집니다.
* **단점:** 에이전트 간의 데이터 상태 변환 및 프로토콜 설계가 어렵고, 조율 실패 시 연쇄 고장(Cascading Failure)의 위험이 큽니다.

## 5. 인간 참여형 (Human-in-the-loop) 4대 패턴 심층 탐구 👥

에이전트가 실무에서 완벽한 자율성을 가질 때 발생할 수 있는 비즈니스 리스크(잘못된 금융 송금, 권한 없는 데이터 파괴, 부적절한 이메일 자동 대량 전송 등)를 원천 차단하기 위해 **인간의 의사결정을 워크플로우 중간에 유기적으로 개입시키는 설계 기법**입니다.

---

### ① 승인 워크플로우 (Approval Workflows)

에이전트가 핵심 비즈니스 액션에 돌입하기 전, 인간이 해당 결정을 검토하고 명시적인 허가(Go-ahead)를 줄 때까지 상태를 대기시키는 패턴입니다.

![Approval Pattern](images/Approval.png)

* **🔧 백엔드 메커니즘 (Under the Hood):**
  * 그래프 컴파일 시 특정 노드 바로 직전에서 멈추도록 설정합니다. (예: `compile(interrupt_before=["write_to_db_node"])`)
  * 에이전트가 `write_to_db_node` 직전에 도달하면, LangGraph는 그래프의 상태를 세이브포인트(Checkpointer)에 영구 보존하고 실행 스레드를 **일시정지(Interrupt)** 시킵니다.
  * 인간 검토자가 외부 UI에서 "승인(Approve)" 버튼을 누르면, 백엔드는 스레드에 보관되어 있던 마지막 상태를 로드하여 그래프 실행을 **재개(Resume)**합니다. 만약 "반려(Reject)"를 누르면, 이전 피드백 처리 노드로 되돌려 보냅니다.
* **💾 상태 변화 시뮬레이션 (State Dict):**
  ```python
  # [1] Interrupt 발생 당시 상태 (Before Approval)
  state = {
      "status": "pending_approval",
      "data_to_write": {"id": 101, "amount": 50000},
      "feedback": ""
  }
  
  # [2] 인간이 '승인' 버튼을 누른 후 재개 직전 상태 (After Approval)
  # 외부 API인 graph.update_state()를 통해 승인 플래그를 주입합니다.
  state = {
      "status": "approved",
      "data_to_write": {"id": 101, "amount": 50000},
      "feedback": "Approved by Compliance Team"
  }
  ```
* **💼 인간 검토자의 액션 목록:**
  * **Approve (승인):** 작업을 그대로 속행하여 다음 단계 노드로 제어 이행.
  * **Reject (반려):** 작업을 기각하고, 반려 사유를 `State["feedback"]`에 적어 이전 기획/생성 노드로 돌려보냄.

---

### ② 입력 대기 (Wait for Input)

에이전트가 당면한 과제를 해결하기 위해 필요한 정보가 부족할 때, 능동적으로 실행을 멈추고 인간에게 텍스트, 옵션 선택 등의 추가 컨텍스트를 수집하는 패턴입니다.

![Wait for Input Pattern](images/Wait_for_Input.png)

* **🔧 백엔드 메커니즘 (Under the Hood):**
  * 에이전트 노드 실행 중 조건부 분기(Conditional Edge)를 통해 사용자 입력이 필요한 노드로 흐름을 보낸 뒤, `interrupt_after=["wait_input_node"]` 설정을 사용해 실행을 대기 상태로 전환합니다.
  * 백엔드는 클라이언트 UI로 "사용자 입력을 대기 중"이라는 메시지와 함께 활성화된 입력 폼(Form) 세션을 전송합니다.
  * 사용자가 입력을 제출하면 `graph.update_state(thread_config, {"user_input": "제출된 텍스트"}, as_node="wait_input_node")`를 호출하여 상태를 업데이트하고 실행 루프를 깨워 다음 단계로 진입합니다.
* **💾 상태 변화 시뮬레이션 (State Dict):**
  ```python
  # [1] 에이전트가 정지하여 질문을 던진 시점 (Before Input)
  state = {
      "agent_question": "출발 예정일이 언제이신가요?",
      "user_input": None,
      "itinerary_planned": None
  }
  
  # [2] 사용자가 '2026-07-01'을 입력한 시점 (After Input)
  state = {
      "agent_question": "출발 예정일이 언제이신가요?",
      "user_input": "2026-07-01",
      "itinerary_planned": None # 이제 다음 노드가 이 날짜를 읽고 여행 계획을 수립함
  }
  ```
* **💼 인간 검토자의 액션 목록:**
  * **Submit (제출):** 텍스트 필드나 날짜 피커, 드롭다운 등을 사용해 정보 전송.
  * **Cancel (취소):** 대화를 종료하고 에이전트 태스크 취소 선언.

### ③ 타임 트래블 (Time Travel)

완성된 결과물이나 이전 실행 과정의 이력을 되돌아보며, 과거 특정 시점의 기록으로 상태를 복원(Rollback)한 뒤 데이터를 수정하여 새로운 비즈니스 시나리오를 재수행하는 고난도 패턴입니다.

![Time Travel Pattern](images/Time_travel.png)

* **🔧 백엔드 메커니즘 (Under the Hood):**
  * LangGraph의 체크포인터는 각 노드 실행(Super Step)이 끝날 때마다 데이터 스냅샷을 생성하고 고유의 `checkpoint_id`를 부여합니다.
  * `graph.get_state_history(thread_config)` API를 호출하면 지금까지 거쳐온 모든 단계의 상태 히스토리가 시간 역순으로 조회됩니다.
  * 사용자가 특정 과거 기록을 지정하면, 백엔드는 해당 `checkpoint_id`의 상태를 타깃으로 로드하고 `graph.update_state()`를 통해 해당 시점의 특정 키 값을 수정한 후, 그 복원된 지점부터 다시 `graph.stream()` 또는 `graph.invoke()`를 실행합니다.
* **💾 상태 변화 시뮬레이션 (State Dict):**
  ```python
  # [1] Step 4 (최종 완료 지점): 블로그 글 작성이 끝났으나 오탈자가 발견됨
  state_at_step_4 = {"step": 4, "text": "에이전트가 만든 완성본 텍스트...", "rating": "Failed"}
  
  # [2] Step 2 (과거 교정 직전 지점)로 되감기한 후 데이터를 강제 수정
  # checkpoint_id = "1ef2-34ab" (Step 2 시점)
  state_at_step_2_modified = {
      "step": 2,
      "text": "인간이 직접 수정한 깨끗한 글 초안...", 
      "rating": "Approved"
  }
  ```
* **💼 인간 검토자의 액션 목록:**
  * **View History (히스토리 조회):** 타임라인 UI를 통해 이전 실행 상태와 로그를 슬라이더나 목록으로 확인.
  * **Fork / Rollback (분기 및 복원):** 특정 과거 시점으로 돌아가 값을 수정하고 재구동(Re-run)하여 새로운 결과 유도.

### ④ 도구 호출 리뷰 (Review Tool Calls)

에이전트가 외부 API나 연산을 수행하기 위해 JSON 인자(Arguments)를 완성했을 때, 이를 백엔드에서 즉시 실행하지 않고 사용자 화면에 매개변수를 노출시켜 검토 및 수정을 허용하는 패턴입니다.

![Review Tool Calls Pattern](images/Review_tool_calls.png)

* **🔧 백엔드 메커니즘 (Under the Hood):**
  * LLM이 출력한 `tool_calls` 정보를 받아 처리하는 도구 실행 노드(`action_node`) 직전에 `interrupt_before=["action_node"]`를 작동시킵니다.
  * 백엔드는 LLM이 만든 호출 스키마(예: `{ "name": "send_email", "args": { "to": "a@b.com", "body": "Hello" } }`)를 상태에 저장하고 일시정지합니다.
  * UI는 이를 사용자에게 텍스트 수정 상자(Input Area) 형태로 렌더링합니다.
  * 사용자는 "a@b.com"을 다른 이메일로 고치거나 이메일 내용을 수정한 뒤 전송을 누르면, 수정된 JSON 데이터가 상태에 저장되며 `graph.update_state()`로 상태 갱신 후 도구 노드가 기동됩니다.
* **💾 상태 변화 시뮬레이션 (State Dict):**
  ```python
  # [1] LLM이 실수로 수신자 주소를 빈 칸으로 만들거나 잘못 적은 상태 (Before Review)
  state = {
      "tool_calls": [
          {"name": "send_email", "args": {"to": "wrong-email.com", "body": "세금 납부 안내서입니다."}}
      ]
  }
  
  # [2] 인간이 UI를 통해 올바른 이메일로 덮어씌운 상태 (After Review)
  state = {
      "tool_calls": [
          {"name": "send_email", "args": {"to": "correct-user@email.com", "body": "세금 납부 안내서입니다."}}
      ]
  }
  ```
* **💼 인간 검토자의 액션 목록:**
  * **Confirm & Execute (확인 및 실행):** 에이전트가 기획한 파라미터를 그대로 인가하여 실행.
  * **Edit Arguments (인자 수정):** 입력 값(이메일 내용, 금액, 쿼리문 등)을 직접 타이핑하여 수정한 후 도구를 우회 실행.
  * **Skip / Block (실행 취소):** 도구 호출을 거부하고 무효 처리하여 에이전트를 다음 생각 노드로 반환.

## ⚖️ 인간 참여형(HITL) 설계 시 핵심 고려사항

1. **사용자 경험 (UX) 설계:**
   * 에이전트가 정지할 때마다 웹소켓 스트리밍 등을 통해 사용자 화면에 명확한 대기 상태 알림과 풍부한 피드백 UI(수정 폼, 타임라인 슬라이더 등)를 렌더링해주어야 대기 지연감을 줄일 수 있습니다.
2. **보안 및 권한 제어 (Security & ACL):**
   * 승인(Approval)이나 도구 호출 리뷰 시, 악의적인 값이나 SQL 인젝션 공격이 `update_state`를 통해 백엔드 상태에 강제 주입되지 않도록 입력값 필터링 및 보안 밸리데이션 검사를 반드시 실행해야 합니다.
3. **타임아웃 및 세션 만료:**
   * 인간 검토자가 자리를 비워 멈춰버린 스레드가 영구적으로 좀비 프로세스가 되지 않도록, 일정 시간(예: 30분) 내 피드백이 없으면 자동으로 반려 처리하거나 세션을 만료시키는 백그라운드 스케줄러를 설계해야 합니다.
